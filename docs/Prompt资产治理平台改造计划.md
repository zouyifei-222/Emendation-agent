## 0. 本版定位与变化

**按包装方案走**：把 Bear Agent 已有的 Skills 自进化与在线评测链路，直接暴露成团队 Prompt / SOP 资产的治理能力。产品要回答的问题就是包装里那句——**「你怎么知道你的 Prompt 变好了」**。

相对 v0.1 的变化：

1. 不再把定位降级为「回归质检 + 版本治理台」，包装里的能力（规则编译、逐规则通过率、单条规则改写、按规则评测、候选对比、优胜登记、使用统计、建议归档）全部列为**建设目标**；
2. 因此**冻结题集从可选项变成必须项**。理由：包装主张「变好了」，而现有考卷来自参与过规则学习的历史，只能证明没退步；只有一批从没参与过学习、锁死不改的题，才能让「变好」这个结论有依据；
3. 补上 v0.1 漏掉的「网页创建 / 编辑规则」；
4. 新增「按指定规则评测」和「评估历史回复」两种模式，并对两者做口径隔离；
5. 包装示例用的是代码审查，涉及读文件，而现有评测只跑纯文本，因此工具型 SOP 的覆盖从可选升级为 P3 必做。

**对外口径约束**（不削弱产品定位，但必须写在报告和界面上）：

- 历史回放题上的分数只能叫「回归表现」，冻结题上的分数才能叫「未见任务表现」，两组必须分列；
- 「规则通过率」不等于「任务成功率」；
- 相关 / 使用判定来自模型，不是客观埋点；
- 本项目自测成绩不是任何公开榜单成绩，也不能与论文数据对标。

## 1. 包装方案与现状的逐条对照

| 包装要求 | 现状 | 结论 |
|---|---|---|
| 团队 Prompt / SOP → 版本化、可人工编辑 | 版本快照、回退已有；网页创建/编辑没有 | 部分已有，P0 补齐 |
| 历史真实对话 → 回放样本池 | 从 `online_provenance.jsonl`、`online_skill_provenance.json` 构造，按会话去重分组 | ✅ 已有，但每条需人工审核 |
| Skill 文本 → 编译成可执行校验规则 | **项目特意移除了从 Skill 关键词自动推导规则**；验收条件由审核者人工填写 | ❌ 需新建（半自动 + 人工确认） |

| 规则越加越多、互相冲突 | 只有版本内避免矛盾，无跨 Skill 冲突检测 | ❌ P2 |
| 全链路可审计 | usage / provenance / history 快照 / 回退日志 | ✅ 已有 |

## 2. 目标架构与数据约定

```text
团队资产层（P2）          负责人 / 状态 / 命名空间 / 评审 / 跨规则冲突检测
        ↓
治理视图层（P0）          网页：创建编辑规则、审核清单、发起评测、看报告、发布与归档
        ↓
评测层（P1，核心）        规则编译 + 稳定规则编号 + 逐规则通过率
                          历史回复合规扫描 / 版本重跑对比（双模式）
                          单规则候选改写 + 冻结题集 + 采纳建议
        ↓
现有内核（不破坏语义）     回放审核 / 双层判分 / 候选 / 冠军 / 使用统计 / 归档 / 审计
        ↓
存储                      .bear/skill-evolution/（现有） + .bear/governance/（新增旁路）
```

**兼容原则**：不修改现有文件语义；新增数据放 `.bear/governance/`；写操作继续走 `state_lock` + 原子替换；现有 `champions.json`、`skill_usage_stats.json`、`history/` 保持可读；新开关默认关闭，保证现有 `/skill-eval` 行为不变。

| 新增文件 | 内容 |
|---|---|
| `.bear/governance/assets.json` | `owner`、`status`(draft/review/active/deprecated)、`scope`、`team`、`last_review_at` |
| `.bear/governance/rules/<lineage>.json` | 稳定 `rule_id` → `{mode, spec, required, source, confirmed_by, confirmed_at}`；来源为「从规则正文抽取，人工确认」 |
| `.bear/governance/holdout/<lineage>.jsonl` | 冻结题：`id`、`task_user`、`context_messages`、`requirements`、`checks`、`never_trained: true`、`frozen_at`、`reviewed_by` |
| `runs/<lineage>/<run_id>/rule_metrics.json` | 按 `rule_id` 聚合 `pass_rate`、样本数、失败样本 ID、涉及版本 |
| `runs/<lineage>/<run_id>/historic_scan.jsonl` | 历史回复合规扫描结果（不重新生成回答，只做规则校验 + 语义判定；语义判定仍需调用判卷模型） |
| `runs/<lineage>/<run_id>/summary.json` | 新增 `holdout`、`rule_metrics`、`recommendation` 字段；`regression` 与 `holdout` 分列 |

#### 3.1 P0 实施结果（已完成，2026-11）

**已交付**：`agents/governance.py`（资产聚合与授权写）、`agents/web.py` 治理路由、`agents/skill_evolution.py::archive_skill_file()`（显式归档）、`web/governance-view.mjs` 渲染模块、`web/index.html` 侧栏入口、`web/app.js` 交互、`web/styles.css` 样式；另修复 Windows 下 UTF-8 规则正文读取、归档目录内文件锁、回退读取编码三处问题。

**实际接口**：`GET /api/governance`、`GET /api/governance/<name>`、`POST /api/governance/save`、`POST /api/governance/<name>/rollback|archive|restore`。写操作沿用本地 Web 的 Cookie auth + `X-Bear-CSRF` + Host/Origin 校验；回退、归档、恢复在前端均需人工 `confirm()`。看板展示规则正文、版本快照数、三项使用统计、冠军与最近报告（**只读展示已有产物，不触发评测**）、审计文件路径与健康状态。

**与计划的有意收窄**（避免把治理写成自动决策）：

1. `agents/governance.py` 提前在 P0 引入，但只做只读聚合 + 委托给现有 skill 文件助手的授权写；资产注册表、状态机、跨规则冲突检测仍属 P2，未实现。
2. 归档是显式人工操作，不是放开自动 prune；看板按「检索 ≥ 12 次且使用 ≤ 0 次」只给**建议**，阈值由 `BEAR_GOVERNANCE_STALE_MIN_RETRIEVED` / `BEAR_GOVERNANCE_STALE_MAX_USED` 配置（默认 12 / 0），与 P1-8 的自动 prune 变量相互独立，且归档随时可恢复。
3. 网页编辑会生成版本快照，但**不会**登记冠军、不会自动发布、不会触发评测；生效规则仍靠人工发布。
4. 路由 / CSRF 用例放在新建的 `tests/test_governance_web.py`，未改动计划里写的 `test_web.py` / `test_web_v3.py`。

**验收结果**：`python -m unittest tests.test_governance_web -v` 6/6 通过；`node --test web/tests/*.test.mjs` 36/36 通过；语法检查与 lint 通过。全量 `python -m unittest discover -s tests` 仍有 4 项失败、8–9 项错误的既有环境性问题（会话文件编码、`read_file` 竞态、真实 SDK 流测试），单独重跑同样失败，与本次改动无关，需另行处理。

**现在能怎么用（举例）**：以「写报告先给结论」这条规则为例。

1. 侧栏进「资产治理」→「新建规则」，填名称和正文「先给结论，再列三条依据」，保存到项目级；列表出现这条规则，版本数 1。
2. 正常使用几天后打开详情：看到正文全文、版本历史、被检索 / 判定相关 / 实际使用次数、冠军与最近报告（没有就留空）、审计路径。若检索 12 次、使用 0 次，页面只标「建议归档」，不自动删除。
3. 想改要求就点「编辑」，改成「先给结论，再列三条依据，最后给风险」，保存后版本数变 2；不满意点「回退」，正文恢复到上一版。
4. 确认不再需要时点「归档」（需二次确认），列表标记「已归档」且仍可查看归档正文；点「恢复」可还原为生效规则。

**现在还做不到**（对应前文「三轮纠正」场景）：从纠正对话自动沉淀增量新规则、按指定规则跑评测、逐规则通过率、冻结题、采纳建议、团队共享都尚未实现。因此「你自己下一次第一次提问就做对」目前没有自动闭环，仍需人工在网页里写规则或改规则；「团队里另一个人第一次就做对」属于 P2。这两条应作为 P1 / P2 的验收判据，不能在 P0 演示里宣称。

### P1　包装的核心链路（本版重点）

| 编号 | 任务 | 改动落点 |

| 改动文件 | `agents/online_skill_eval.py`、`agents/skill_evolution.py`、`agents/main.py`、`agents/web.py`、`web/governance-view.mjs`、`docs/runtime-hardening.md`、`README.md` 评测章节 |

#### 3.2 P1 第一段实施结果：冻结评测边界（2026-11）

**外部参考与归属**：本段按 MIT 许可复用两个开源项目的**数据契约与规则定义**，没有复制任何源码（两者均为 TypeScript / Node 生态，本仓库是单进程 Python，无法直接 import）。具体实现均为本项目自写，落在 `agents/governance_eval.py`，文件头与本节保留来源说明；SkillOps 的 24 条 lint 规则和 SkillHone 的 CLI 未移植。

## 11. 大白话版：怎么评测、标准是什么、指标是什么、以后怎么用

> 这一节不写任何文件名、命令和英文术语，可以直接给团队里不写代码的人看。
> 注意：本节讲的是改造完成后的用法。现在网页已能创建 / 编辑规则、按规则评测、看采纳建议与逐条通过率、切换状态、查冲突；工具型 SOP 需单独运行，多人协作尚未做，见 3.3 节。

### 先说一句最重要的

如果你现在一条规则、一次真实使用记录都没有，是没法评测的。评测不是凭空考模型，它得拿以前真实发生过的任务当考卷。所以第一步不是测，是先把东西攒出来。

### 第一步：先准备三样东西

先把你要管的规则写下来。别贪多，先挑一两条最痛的，比如「代码审查必须列出安全风险」「写报告必须先给结论」。

然后正常用起来，在网页里像平时一样派活，用上几天。系统会自动记下：这次找了哪条规则、找得对不对、最后到底用没用上、你后来有没有纠正它。这些记录就是以后的考卷来源，不用自己编题。

等攒够几次真实对话，再开始评。如果实在等不及，就手工准备六到十道最典型的题，定好标准后锁死不再改，以后每次都拿同一套题考。这是唯一需要编题的情况，而且只编一次。

### 第二步：给每道题定标准

标准是人定的，不是系统从规则里自动读出来的。因为「规则写了要有安全风险章节」和「怎么才算写对了」是两回事，机器猜不出来。改造做完之后，系统会把规则里看起来像要求的地方先抽出来给你看，你点确认才算数，不会自己偷偷生效。

每道题定两类标准：

一眼能判的硬标准，比如必须按某种格式输出、必须出现某段话、段落不能超过几段。这个由程序判，快且确定。

需要理解意思的软标准，比如「给的建议是不是真能照着做」「结论有没有依据」。这个交给另一个模型判卷，会给出理由。

定标准的人得是懂业务的同事，定完就锁住，之后不许改，否则这次和下一次的分数没法比。

### 第三步：在哪测、怎么测

网页端就能测。打开工作台，侧栏进评测页，选要评的那条规则，点运行评测就行。命令行也能测，效果一样，网页上那个按钮本质就是替你发了同一条指令，不用两边都开。

点下去之后，机器做两件事：

第一件，把以前那些真实回答翻出来，按你定的标准查一遍，看看过去有多少回复不合规。这只是体检，不用来判谁赢。

第二件，让当前版本和自动生成的候选版本，在同一批题上各自重新答一遍，程序查格式、另一个模型查语义，然后比分数。判的是新答案，不是老答案，这样才公平。

跑完在同一页看报告。点运行评测会真的调用模型，会产生费用；不点就不会花钱，光看旧报告不花钱。

### 第四步：看哪些数

规则通过率：所有检查项里通过了多少比例。这是最该盯的数，而且要能按每一条规则单独看，比如「必须列出受影响的调用方」这条只有百分之四十。

单题得分：硬标准分量重、软标准分量轻，加权算出来的分。

平均分：所有题的单题得分取平均。

提升幅度：新版比旧版高了多少。不够门槛就不算赢。

硬标准失败次数：只要挂了一条硬标准，其他分再高也直接不通过。

两组分数分开看：一组是历史题上的表现，只能说明没退步；另一组是锁死的、从没拿来学过的题上的表现，才稍微能说明没变差。这两组绝对不能混着报。

新旧对比：当前版、候选版、已有优胜版，三个一起摆出来比。

采纳建议：报告直接给「建议采纳」「建议保留当前版」或「数据不够，先别动」。

使用健康度：这条规则被翻出来多少次、判定相关多少次、真正用上了多少次。长期被翻出来却一次没用上，就给归档建议。

有个坑一定要记住：规则通过率不等于任务真的做成了。格式全对但内容胡说，硬标准照样满分。所以报告里要抽检几条实际回答，别只看数字。

### 第五步：结果不好怎么办

可以自己动手改规则，也可以让系统只改写得最差的那一条，生成一两个新版本，再拿同一批题重跑一次。比完确认硬标准没挂、两组分数都没退步、提升也够，才建议采纳。

采纳不等于立刻生效。登记成优胜版本之后，还要人点一下发布；觉得不对随时回退到上一版。

### 第六步：以后日常怎么用

平时该干嘛干嘛，在网页里正常派任务。系统自己翻规则、自己决定这次用哪条，自动记使用情况和你的反馈，不用你管评测。注意不是手动选一条规则来调用，所以才会有「被翻出来很多次、却一次没用上」这种情况。

有人想加规则或改规则时，不要直接改生效版本：先变成候选，跑一次评测，看了报告再决定发布。

建议的节奏是每次改完规则跑一次，或者固定每周跑一次。看报告的顺序是：先看有没有挂硬标准，再看两组分数有没有退步，再看提升够不够，最后才决定发不发。

每个季度看一次使用健康度，把长期没人用的规则归档。归档不是删除，随时能恢复，这样才敢删。

出了问题时，点开报告能一路看到：哪条规则在哪道题上没过、当时实际答了什么、判卷给的理由、这一版是谁改的、什么时候发布的。这就是追溯。

### 最后，哪些话不能说

不能说「系统证明提示词变强了」，只能说「在这些题上没退步、通过率更高了」。

不能说「达到某某榜单水平」，本项目自测和公开榜单不是一回事。

不能说「某条规则没用，系统自动删了」，相关和使用是模型判断的，低频也不等于没用，尤其合规类规则可能一年才用一次。

### 一句话串起来

先写规则，正常用几天攒真实记录，给十来道题定好标准并锁死；以后每次改规则就在网页选这条、点一次运行评测；看逐条通过率、两组分数和新旧对比，没退步才发布；定期把没人用的规则归档，随时能恢复。全程不用一道题一道题手工测，也不用生成几百道考题。人只花在「定标准」和「拍板发布」两件事上，其余都是机器批量跑。
